# EN751627 BootROM extension and chainloader

`bootext.bin` combines the C DRAMC stage and the interactive XMODEM
receiver in FE SRAM. The internal BootROM enters it at `0x9fa30000`, as
specified by the supplied SDK's `spram_ext/ld_ext_en7516.script`.

## Build

```sh
make CROSS_COMPILE=mips64-linux-gnu- en751627-bootext
make LLVM=1 en751627-bootext
```

The output is `out/en751627/bootext.bin`. The intermediate DRAMC and
receiver images are `out/en751627/.bootext/dramc.bin` and
`out/en751627/.bootext/chainloader.bin`. They can be built separately with
`en751627-bootext-dramc` and `en751627-bootext-chainloader`.

The separate `en751627-chainload` target builds the post-DRAM flash
payload reader used by TCBoot. It is not the image sent to the BootROM to
initialize DRAM. `en751627-tcboot` still packages the normal flash boot
flow; its DRAMC returns to boot2 instead of entering the XMODEM receiver.

## SRAM layout

| Cached address           | Use                                            |
| ------------------------ | ---------------------------------------------- |
| `0x9fa30000`             | DRAMC entry, code, data and BSS                |
| `0x9fa35000`             | XMODEM receiver entry, code, CRC table and BSS |
| `0x9fa3b000..0x9fa3ffff` | Reserved for the DRAMC stack                   |

The DRAMC uses the uncached stack address `0xbfa3fff0`. Its bootext entry
sets `SYS_BOOT_JUMP` (`0xbfb00280`) to `0x9fa35000`. The build checks the
DRAMC runtime end, receiver entry, receiver BSS end and padded image size,
so neither component can overlap the next component or the stack reserve.
Both payloads must fit below `0x9fa3b000`; FE SRAM itself is 64 KiB.

After calibration the DRAMC invalidates its temporary KSEG2 TLB mappings.
The receiver restores the low DRAM apertures using the register sequence
from `flash/en751627/boot2.S`, then establishes a cached DRAM stack and
clears its own BSS. Cache maintenance uses Config1 geometry for L1 and
Config2 geometry for the 1004K L2, in L1-D/L2/I-cache order. The same
writeback/invalidation sequence runs before handing control to U-Boot.

The SDK's secondary-context preparation is retained through the BootROM
launch records at `0xbfa40140`. Ready contexts 1..3 execute a stackless
callback that clears Cause.WP and returns to the BootROM wait loop at
`0xbfa40040`. A launch that does not acknowledge within the polling limit
stops the receiver; unavailable or already launched contexts are skipped.
This relies on the internal BootROM having initialized its GDMP SRAM
wait code and launch records.

## Use

Send `bootext.bin` through the internal BootROM's extension-loading path
for FE SRAM at `0x9fa30000`. After calibration, the receiver offers the
common chainloader menu. `x` receives U-Boot through XMODEM and boots it;
the default raw load/entry address is `0x81000000`. Raw, uncompressed
legacy, supported FIT and ECNT inputs use the existing parsing and CRC
checks described in [`chainloader/README.md`](../chainloader/README.md).
The receiver checks its own per-128-byte CRC table before accepting a
payload; this table covers the receiver, not the preceding DRAMC image.

`b` receives the existing 1 MiB TCBoot flash image, stages it completely
in DRAM, and uses the common erase/write/readback backend. The current
backend supports contiguous SPI-NAND with on-die ECC, using the page
shift left by the BootROM at `0xbfa40020`. SPI NOR and controller-ECC boot
mode are rejected before erase; controller-ECC/OOB generation and
bad-block remapping are not implemented here. Controller-ECC mode is
identified by bit 23 of `SYS_GLOBAL_PARM`, matching the SDK definition.

## Validation limits

GCC and Clang builds were checked for embedded payload equality, CRC
tables, entry addresses and SRAM/BSS bounds. Modeled execution also
checked startup, BSS clearing, low DRAM aperture writes, L1/L2 traversal,
payload handoff and the secondary-context launch protocol. These checks
do not exercise the physical DDR, cache coherency between real cores,
UART timing, BootROM download protocol or flash hardware. Cold boot,
XMODEM transfer, memory stress and flash readback on an EN751627 board
remain necessary for hardware validation.
